# ADR-005 — Internal clinical model and the evidence/provenance layer

**Status:** Accepted
**Date:** 2026-09-15

## Context

Two failure modes must be structurally impossible, not merely discouraged:

1. **The internal database being a FHIR mirror.** FHIR is an *interoperability* standard: it is
   verbose, optimised for exchange, and full of optionality. Using it as the operational schema
   makes clinical reasoning queries painful and couples the product to a standard that changes on
   its own schedule.
2. **Untraceable clinical facts.** If a summary says "chest pain for 2 hours", a physician must be
   able to click it and see the exact utterance, timestamp, and confidence that produced it. If
   that chain cannot be reconstructed, the AI output is not clinically usable.

## Decision

**A canonical internal clinical model, separate from FHIR.** FHIR R4 is produced by an explicit
mapper at the boundary (ADR-006 of the interoperability set). The internal model is optimised for
clinical reasoning, evidence provenance, validation, longitudinal analysis, human review and
FHIR mapping.

**Every clinically meaningful fact carries provenance.** Three distinct origin classes are
first-class and never mixed:

| Class | Meaning | Example |
|---|---|---|
| `PATIENT_REPORTED` | The patient said or selected it | "I have fever" |
| `DOCUMENT_DERIVED` | Extracted from an uploaded document | "Temperature 102.1 F" on a lab report |
| `CLINICIAN_ENTERED` | A physician or nurse typed it | A corrected dosage |
| `AI_INFERRED` | Generated by a model, always labelled as such and always requiring physician review | "Possible infectious syndrome" |

The evidence layer is implemented as:

```
Evidence (immutable)                     ClinicalClaim (derived)
  id                                       id
  type          answer|ocr|vital|doc|prior  subject_ref   -> Symptom | LabResult | ...
  source                                     statement
  source_ref    questionnaire_response_id    evidence_ids[] -> Evidence
  raw_value     never destroyed              origin_class
  normalized_value                           confidence
  confidence                                 verification_state
  captured_at                                generated_by   provider + model + prompt version
  created_by
```

Rules enforced in code:
- `Evidence.raw_value` is **immutable**. Normalisation writes `normalized_value` beside it; the
  original patient wording is never destroyed. This is what makes code-mixed and relative-date
  handling auditable.
- A `ClinicalClaim` with an empty `evidence_ids` array is **rejected at construction**. This is
  the mechanical enforcement of "if evidence is absent, do not generate the claim".
- `origin_class = AI_INFERRED` is rendered differently in the physician console and cannot be
  auto-accepted.
- `verification_state` transitions are `UNVERIFIED -> VERIFIED | REJECTED | CORRECTED`, and only a
  clinician role may perform them.

**Symptoms are modelled with a formal SOCRATES sub-state** (Site, Onset, Character, Radiation,
Associated symptoms, Timing, Exacerbating/relieving, Severity) plus `certainty`, `source`,
`confidence`, `verified_at` and `verified_by`. Each complaint carries its own SOCRATES state, and
pathways only ask the SOCRATES dimensions that are relevant to that complaint
(see ADR-008 for the interview engine).

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| Store FHIR resources as the operational schema | Poor query ergonomics for clinical reasoning and timelines; couples the internal model to an external standard's release cycle; loses the crisp provenance separation the product depends on |
| Free-text clinical notes with an LLM reading them later | Destroys structure, makes validation and measurement impossible, and makes the LLM the source of truth — explicitly forbidden |
| A generic `observations` table holding everything as key/value | Eliminates type safety, foreign keys and meaningful indexes; makes clinical queries unverifiable and the schema undocumentable |
| Store the AI prompt and response as the clinical record | The record must be the structured fact, not the model's raw output. Raw output is retained *for audit*, never as the source of truth |
| A full RDF/graph database | The relationship structure needed is modest and traversable with indexed relational queries. A graph database adds an operational dependency (and is unavailable locally) without a demonstrated need |

## Consequences

**Positive**
- The evidence trace WOW feature is not a UI trick — it is a read of real stored provenance.
- Contradiction detection is possible *precisely because* origin classes and sources are separated:
  "patient says no medications" (PATIENT_REPORTED) vs "a prior prescription lists one"
  (DOCUMENT_DERIVED) is a structurally detectable conflict.
- The LLM is structurally incapable of writing an unsupported claim into the record.
- FHIR mapping is a pure function of the internal model, and therefore unit-testable without a
  server.

**Negative / accepted**
- More tables and more joins than a naive design; query helpers are provided in the repository
  layer so feature code stays readable.
- The evidence table grows faster than the clinical tables. Managed with indexes on
  `(tenant_id, source_ref)` and a documented retention policy — evidence is retained as long as
  the clinical record it supports.
